# Go Stock Replica Design

## Goal

Build an independent, functionally equivalent desktop stock-analysis application based on the current go-stock codebase, while removing dependence on the original author's hosted services, branding, update channel, donation/VIP ecosystem, and private operational assumptions.

The first successful outcome is a Windows desktop app that can be built, launched, configured, and used for core stock workflows without access to any `go-stock.sparkmemory.top` service or original-author account.

## Scope

This project is a controlled replication and independence effort, not a full product rewrite.

In scope:

- Keep the Wails + Go + Vue desktop architecture.
- Keep local SQLite persistence.
- Keep core self-selected stock workflows: watchlist, groups, cost price, price refresh, alerts, K-line charts, market data views, funds, news, research reports, AI analysis, prompt templates, cron tasks, MCP and skills management where feasible.
- Replace original-author hosted dependencies with local behavior, user-configured endpoints, or new provider abstractions.
- Rebrand visible application identity and remove original donation/community content.
- Add a service-dependency inventory so unstable interfaces are known and testable.
- Produce a buildable, maintainable fork that can later be released under GPLv3-compatible terms.

Out of scope for the first replica:

- Rebuilding the app as a SaaS or browser-first web product.
- Implementing paid membership, cloud accounts, billing, or a new community platform.
- Guaranteeing all third-party financial data sources remain stable.
- Reproducing the original author's private prompt plaza, share service, VIP code issuer, news sync service, or CDN.
- Legal/commercial validation of financial data redistribution rights.

## Current Architecture

The existing project is a Wails desktop application.

- `main.go` starts the desktop app, embeds `frontend/dist`, initializes SQLite, loads embedded stock basics, starts cron tasks, and also launches a small `ai-assistant-web` HTTP service.
- `app.go` exposes the large Wails API surface used by the Vue frontend.
- `app_common.go` contains shared Wails methods for market data, AI, prompts, stock changes, all-stock info, and fund-flow views.
- `backend/data` contains most market, fund, K-line, AI, settings, prompt, data-source, notification, and utility APIs.
- `backend/agent` contains agent-mode AI orchestration, tool calling, memory, Feishu bot support, and cron task execution.
- `frontend/src` contains the Vue/Naive UI application.
- `ai-assistant-web` is an embedded web sub-service, not the main app.
- `data/stock.db` is the default local SQLite database path.

This structure should remain recognizable during the first replica phase.

## Target Architecture

The replica should introduce independence through adapters and configuration rather than a large rewrite.

### Desktop Shell

The main app remains a Wails desktop app. The Windows build artifact remains a single executable generated by `wails build`.

The desktop shell owns:

- Startup and shutdown.
- SQLite initialization.
- Embedded assets.
- Native notifications.
- Window sizing and theme.
- Wails method binding.

### Local Persistence

SQLite remains the default persistence layer.

The replica must preserve:

- Settings.
- AI model configs.
- Followed stocks and groups.
- Prompt templates.
- Saved AI analysis results.
- Cron tasks.
- MCP server and skill records.
- Trading records.

Schema changes should be additive in the first phase.

### Provider Layer

The replica should gradually introduce provider boundaries around unstable external calls.

Provider categories:

- Market data provider: real-time quote, minute line, K-line, stock basics, market statistics.
- News provider: market news, telegraph, hot topics, hot stocks, events, calendar.
- Research provider: announcements, research reports, industry reports.
- Fund provider: fund search, ranking, K-line, holdings, net value.
- AI provider: OpenAI-compatible and named platform model configs.
- Share provider: export/share behavior.
- Update provider: version check and release download.
- Prompt library provider: local prompt templates first, optional remote prompt plaza later.

Initial implementation may wrap existing `backend/data` methods instead of rewriting them immediately, but new code should call the provider boundary where practical.

## External Dependency Policy

The replica must classify every external dependency into one of four types.

Type A: User-configured service

- AI model providers.
- Tushare token.
- Feishu and DingTalk webhooks.
- MCP servers.
- HTTP proxy.

The app may keep these features, but must fail gracefully when not configured.

Type B: Public data endpoint

- Sina quote.
- Tencent quote.
- Eastmoney APIs.
- Cailianpress APIs.
- Xueqiu hot stock endpoints.
- Timor holiday API.
- Wallstreetcn APIs.

The app may use these, but each call should have timeout, empty-data handling, and user-visible failure states.

Type C: Original-author hosted service

- `go-stock.sparkmemory.top`.
- Original share upload service on port `16688`.
- Original news sync endpoint.
- Original prompt plaza default endpoint.
- Original device-binding API.
- Original GitHub release channel.

These must be removed, disabled by default, or replaced with replica-owned configurable endpoints.

Type D: Static upstream project reference

- Original GitHub URLs in About page.
- Original logo and payment images.
- Original community links.

These must be replaced during rebranding.

## Branding And Licensing

The project license is GPLv3. A distributed derivative should comply with GPLv3 obligations.

Replica branding requirements:

- New application name.
- New icon and splash/about assets.
- New About page copy.
- Remove original author donation QR codes.
- Remove original QQ/community links.
- Remove original sponsor/VIP upsell copy.
- Replace update URLs.
- Add a clear investment risk disclaimer.
- Add a GPLv3 attribution and source availability notice.

The first internal build may keep code package names, but visible UI branding must change before distribution.

## Feature Strategy

### Keep First

These features are core and should be preserved early:

- Watchlist and group management.
- Cost price and position fields.
- Real-time price refresh.
- Local alerts.
- K-line charts with fallback sources.
- Market/news panels where public endpoints still work.
- AI analysis using user-provided model config.
- Prompt template management.
- Settings import/export.

### Defer

These features should not block the first independent release:

- Prompt plaza remote account system.
- Share-to-cloud analysis pages.
- VIP2 Web AI assistant gate.
- Device binding.
- Original-author automatic update mirror.
- Cloud membership or paid tiers.

### Replace

These features need replica-specific alternatives:

- Share analysis: replace with local Markdown/Word/image export first.
- Prompt plaza: replace with local prompt template library first.
- Update checks: replace with disabled-by-default or new GitHub repo endpoint.
- VIP gates: remove, or replace with local feature flags until a real license model exists.

## Error Handling

Every replicated external call should behave predictably.

Required behavior:

- Missing API key returns a configuration hint, not a panic.
- Network timeout returns a user-visible empty/error state.
- Unsupported market type returns a typed error.
- Third-party response parse failure logs the source and returns empty data.
- Background cron failures are logged and surfaced in cron status where applicable.
- AI failures should preserve the user's question and show provider error text.

## Testing Strategy

The first phase should use a practical safety net rather than exhaustive coverage.

Required checks:

- `npm --prefix frontend run build`
- `go test ./... -run '^$' -count=0`
- `wails build`

Focused tests should be added around new provider boundaries:

- Settings defaults without original-author endpoints.
- Provider selection.
- Share provider local export fallback.
- Update provider disabled state.
- VIP/feature gate removal or local replacement.
- External dependency inventory parser if implemented as code.

Manual smoke tests:

- Launch desktop app.
- Create or open SQLite database.
- Add a stock to watchlist.
- Refresh real-time price.
- Open K-line chart.
- Configure an AI provider.
- Run one AI analysis.
- Save/export analysis locally.
- Open settings and About page.

## Success Criteria

The replica is successful when:

- It builds on Windows using the documented Go, Node, npm, and Wails versions.
- The executable launches without original-author service access.
- Core watchlist, quote, K-line, settings, and AI workflows work with user-owned configuration.
- Original-author hosted endpoints are not required for normal use.
- Original branding and donation UI are removed from distributed builds.
- Failure states are understandable when third-party data sources are unavailable.
- A dependency inventory documents all remaining external calls.

## Non-Goals

The replica should not:

- Scrape paid or protected data sources in a way that bypasses access controls.
- Pretend to provide investment advice.
- Hide its GPLv3 obligations.
- Keep original donation, VIP, or device-binding flows as if they belonged to the replica.
- Rewrite the whole application before proving the independent build works.

## Open Decisions

These decisions can be made during implementation:

- Final product name and icon.
- Whether to keep `ai-assistant-web` after removing VIP gates.
- Whether update checks should be fully removed or pointed at a new GitHub repo.
- Whether prompt plaza becomes local-only or configurable remote.
- Whether to keep package/module name `go-stock` for internal builds.
